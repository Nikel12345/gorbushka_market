# Gorbushka Market

Маркетплейс для рынка. Монорепозиторий: `backend/` (Django + DRF) и `frontend/` (React + TypeScript + Vite).

## Быстрый старт

### Backend

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements/dev.txt
copy .env.example .env          # по желанию: без .env работают dev-дефолты
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver      # http://127.0.0.1:8000
```

### Frontend

```bash
cd frontend
npm install
npm run dev                     # http://localhost:5173
```

В dev-режиме Vite проксирует `/api/*` на Django, поэтому фронт и API работают с одного origin.

## Авторизация

Сессии Django (HttpOnly cookie `sessionid`) + CSRF. Один тип аккаунта, вход по email. Админка магазина — для сотрудников (`is_staff`, есть в `/auth/me/`).

| Метод | URL | Описание |
|---|---|---|
| GET  | `/api/v1/auth/csrf/`     | выставляет cookie `csrftoken` |
| POST | `/api/v1/auth/register/` | `{email, password, first_name?, last_name?}` → пользователь, сразу залогинен |
| POST | `/api/v1/auth/login/`    | `{email, password}` → пользователь |
| POST | `/api/v1/auth/logout/`   | 204 |
| GET  | `/api/v1/auth/me/`       | текущий пользователь (`is_staff` — доступна админка магазина), 403 если не авторизован |

- Все небезопасные запросы (POST/PUT/PATCH/DELETE) требуют заголовок `X-CSRFToken` со значением cookie `csrftoken` — `shared/api/client.ts` делает это сам.
- login/register ограничены по частоте (`THROTTLE_RATE_AUTH`, по умолчанию 10/min с IP).
- Email хранится в нижнем регистре, вход регистронезависимый.

## Лента товаров (главная)

Публичные эндпоинты, авторизация не нужна.

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/v1/catalog/categories/` | дерево категорий для меню каталога (см. «Категории») |
| GET | `/api/v1/catalog/products/` | лента товаров на продаже |
| GET | `/api/v1/catalog/products/{id}/` | товар (с описанием, остатком, путём категории, характеристиками и вариантами — см. «Варианты товара») |
| GET | `/api/v1/catalog/products/{id}/reviews/` | отзывы о товаре (см. «Отзывы») |
| GET | `/api/v1/catalog/products/{id}/bought-together/` | «С этим товаром часто покупают» (см. ниже) |

Параметры ленты (все необязательные, комбинируются):

| Параметр | Пример | |
|---|---|---|
| `q` | `чехол iphone` | поиск: все слова в названии/описании, без учёта регистра, ё = е |
| `shop` | `12` | товары магазина |
| `category` | `5` | товары категории вместе с подкатегориями |
| `price_min`, `price_max` | `1000`, `5000` | диапазон цены в рублях (как на витрине), включительно |
| `in_stock` | `true` | только в наличии |
| `group` | `7` | товары группы вариантов |
| `sort` | `new` (по умолчанию), `price_asc`, `price_desc` | сортировка |
| `page_size` | `20` (по умолчанию), до 50 | размер порции |
| `cursor` | значение `next_cursor` | следующая порция |

Ответ: `{"next_cursor": "..." | null, "results": [...]}`. У карточки и товара есть `rating` — средняя оценка
по отзывам строкой (`"4.75"`, `"0.00"` — отзывов нет) и `reviews_count`.

**Бесконечная прокрутка (курсорная пагинация).** Первый запрос — без `cursor`. Следующий — с теми же
фильтрами и `cursor=<next_cursor>`. `next_cursor: null` — лента закончилась. При изменении любого
фильтра или сортировки ленту начинают заново без курсора (курсор от другой сортировки вернёт 400).
Курсор — непрозрачная строка, фронт не должен её разбирать. Внутри — позиция последнего товара
`(значение поля сортировки, id)`, а запрос строится как `WHERE <фильтры> AND (field, id) > (позиция)`,
поэтому нет дублей/пропусков при добавлении товаров во время прокрутки и нет замедления на глубине.
Общего количества (`count`) нет намеренно — это лишний `COUNT(*)` на каждый запрос.

### Реклама в ленте

`GET /api/v1/promo/feed/` (публичный) — одна случайная реклама из показываемых:

```json
{"id": 1, "title": "Скидки недели", "image": "/media/promo/<uuid>.png",
 "image_mobile": "/media/promo/<uuid>.png" | null,
 "url": "/" | "https://..." | ""}
```

- Где и когда показать рекламу, решает фронт; бэк только отдаёт запись. Полосы **не входят в
  страницы ленты**: курсор, `page_size` и ответ `/catalog/products/` не меняются.
- Каждый запрос — новая случайная полоса (повторы возможны). Запрашивать один раз на рекламное
  место и хранить результат, иначе при перерисовке полоса сменится.
- Нет ни одной показываемой полосы — `204` без тела: место не показывать.
- `image_mobile` — узкая версия для телефона, `null` — показывать `image`.
- Полоса — просто ссылка `url`: путь на сайте (`/`, `/?q=чехол`, `/products/7`) или http(s)-адрес
  (`javascript:` и `//чужой-сайт` бэк не пропускает); пусто — полоса без ссылки.
  Миграция `promo/0003` направила все существовавшие полосы на главную (`/`).
- Показываются включённые полосы в своём периоде (`starts_at` / `ends_at`). Заводятся в админке
  («Реклама»); `position` — только порядок в админке.
- Не называйте классы и пути словами `ad`, `ads`, `banner` — блокировщики рекламы прячут такие элементы.

## Доставка

Справочник способов ведёт маркет в админке. Сейчас (засеяно миграцией):

| code | Способ | Исполнитель | Цена | Срок | Выбор времени |
|---|---|---|---|---|---|
| `pickup` | Самовывоз из магазина | магазин (`shop`) | 0 | — | нет |
| `market_courier` | Доставка курьером | служба доставки (`market`) | 50 | 1–2 дня | дата + интервал (10–14, 14–18, 18–22) на 7 дней |

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/v1/delivery/methods/` | активные способы: `id, code, name, kind, provider, description, price, eta, requires_address, has_slots` |
| GET | `/api/v1/delivery/methods/{id}/slots/` | доступные `[{date, window_id, start, end}]`; для способов без выбора времени — `[]` |

- `eta` — `{"min_days", "max_days"}` или `null` (у самовывоза срока нет).
- Слоты начинаются с «сегодня + min_days» (время Москвы); уже начавшиеся сегодня интервалы не предлагаются.
- `provider` — кто везёт: от него будет зависеть группировка товаров при оформлении
  (доставка продавца — в пределах магазина, логистика маркета сможет объединять магазины).
- Какие способы магазин может назначать товарам — `DeliveryMethod.objects.available_for_shop(shop)`
  (сейчас все активные; сюда же ляжет подключение магазина к логистике маркета).

## Корзина

Хранится на бэке, требует авторизации. **Каждый запрос возвращает корзину целиком** — повторный GET не нужен.

| Метод | URL | Описание |
|---|---|---|
| GET    | `/api/v1/me/cart/` | содержимое |
| DELETE | `/api/v1/me/cart/` | очистить |
| POST   | `/api/v1/me/cart/items/` | `{product_id, quantity=1}` — положить; если товар уже в корзине — количество прибавляется (201) |
| PATCH  | `/api/v1/me/cart/items/{product_id}/` | `{quantity}` — задать количество; **`0` — убрать товар**; товара нет в корзине — 404 |
| DELETE | `/api/v1/me/cart/items/{product_id}/` | убрать товар (повторно — не ошибка) |

Ответ:
```json
{
  "items": [
    {
      "product": {"id": 7, "title": "iPhone 15", "price": "1000.00", "image": null, "in_stock": true,
                  "shop": {"id": 1, "name": "Павильон 12"}, "created_at": "..."},
      "quantity": 2,
      "total": "2000.00",
      "is_available": true,
      "available_quantity": 5
    }
  ],
  "items_count": 2,
  "total_amount": "2000.00",
  "has_unavailable": false
}
```

- `product` — та же карточка, что в ленте (`ProductCardSerializer`), фронту не нужно догружать товары.
- Цена в корзине всегда текущая; фиксируется только при оформлении заказа.
- Увеличить количество можно, только если товар на продаже и его хватает (иначе 400 с `code`:
  `product_unavailable` / `insufficient_stock`). Уменьшить или убрать — всегда.
- Если после добавления товар раскупили или сняли с продажи — позиция остаётся с `is_available: false`
  и `available_quantity` (сколько можно купить сейчас); в `total_amount` она не входит, `has_unavailable: true`.
- Лимиты: до 999 шт. одной позиции, до 100 разных товаров.

## Оформление заказа

Структура покупки:

```
Purchase  покупка: покупатель, способ и статус оплаты, items_total + delivery_total = total_amount
 ├── Order     заказ = магазин × отправка: shop, shipment, status, total_amount (товары)  ← его видит продавец
 │    └── OrderItem  товар, снимок цены
 └── Shipment  отправка: способ доставки, магазин (самовывоз), адрес, слот, цена доставки
```

У каждого заказа ровно один способ доставки: если покупатель забирает чехол сам, а iPhone того же магазина
везёт курьер — в админке два заказа.
Доставка в ответах — `order.shipment`; `items[].shipment` устарело (дублирует его, оставлено для совместимости).

Способ доставки покупатель выбирает **у каждой позиции**. Позиции с одинаковой доставкой бэкенд объединяет
в отправку, и доставка оплачивается **один раз за отправку**: доставка курьером — одна отправка на все товары,
самовывоз — отдельная отправка. Правило — `orders.checkout.shipment_key`.
Время выбирается одно на способ доставки, адрес — один на покупку.

| Метод | URL | Описание |
|---|---|---|
| GET  | `/api/v1/me/checkout/` | страница оформления (ничего не сохраняет) |
| POST | `/api/v1/me/checkout/quote/` | `{items}` → отправки и суммы для выбранных способов (ничего не сохраняет) |
| POST | `/api/v1/me/checkout/` | оформить → `201` + покупка как в `/me/purchases/{id}/` |

`GET /me/checkout/`:
```json
{
  "items": [
    {"product": {...карточка...}, "quantity": 2, "total": "2000.00", "is_available": true, "available_quantity": 5,
     "delivery_methods": [{...как в /delivery/methods/...}], "pickup_address": "1 этаж, A-1"}
  ],
  "unavailable_items": [
    {"product": {...}, "quantity": 1, "...": "...", "problem": {"code": "product_unavailable", "detail": "..."}}
  ],
  "items_total": "2000.00",
  "payment_methods": [{"code": "balance", "name": "С баланса"}, {"code": "on_delivery", "name": "При получении"}],
  "balance": "1500.00",
  "bonus": "300.00",
  "bonus_max_share": "0.50",
  "can_checkout": true
}
```

- `balance` — доступные деньги (для оплаты с баланса); `bonus` и `bonus_max_share` — для переключателя
  «оплатить бонусами» (спишутся все бонусы, но не больше этой доли итога).

- `items` — что будет оформлено; `delivery_methods` — способы на выбор для этой позиции.
- `unavailable_items` — не оформляются и остаются в корзине. `problem.code`: `product_unavailable` (снят / закончился),
  `insufficient_stock` (в корзине больше, чем есть), `own_product` (товар своего магазина), `no_delivery` (нет способа).
- Самовывоз из магазина без адреса не предлагается.

`POST /me/checkout/quote/` — `{"items": [{"product_id": 7, "delivery_method_id": 2}, ...], "use_bonus": true}`:
```json
{
  "shipments": [{"delivery_method": {"id": 2, "code": "market_courier", ...}, "shop": null, "price": "50.00", "product_ids": [7, 9]}],
  "items_total": "2450.50", "delivery_total": "50.00", "total_amount": "2500.50",
  "bonus_amount": "300.00", "amount_to_pay": "2200.50"
}
```

`POST /me/checkout/`:
```json
{
  "items": [{"product_id": 7, "delivery_method_id": 2}, {"product_id": 9, "delivery_method_id": 1}],
  "slots": [{"delivery_method_id": 2, "date": "2026-10-16", "window_id": 3}],
  "address": "ул. Барклая, 8, кв. 5",
  "payment_method": "balance",
  "use_bonus": true,
  "comment": "Позвонить заранее",
  "expected_total": "2500.50"
}
```

- `items` — **ровно** позиции из `items` превью, у каждой — способ из её `delivery_methods`.
- `slots` — для каждого выбранного способа с `has_slots` (слоты — `/delivery/methods/{id}/slots/`).
- `address` — обязателен, если выбран способ с `requires_address`. Для самовывоза в отправку пишется адрес магазина.
- `expected_total` — итог, который видел покупатель (из `quote`), **до бонусов** (`total_amount`).
- `use_bonus` — переключатель «оплатить бонусами» (по умолчанию `false`): бонусы списываются сразу при любом способе
  оплаты, остаток (`amount_to_pay`) — по `payment_method`.
- `payment_method`: `balance` — остаток сразу списывается с доступных денег (`payment_status: paid`),
  `on_delivery` — остаток платится при получении (`unpaid`; сколько взять — `amount_due` у заказа и отправки).
- Всё в одной транзакции: заказы по магазинам, отправки, списание остатков, оплата, удаление купленного из корзины.
  Любая ошибка откатывает всё.

Ошибки:

| Код | HTTP | Что делать фронту |
|---|---|---|
| `cart_changed` | 409 | корзина изменилась (в т.ч. повторное нажатие) — перечитать `GET /me/checkout/` |
| `total_changed` | 409 | сумма изменилась — показать новую (`quote`) и попросить подтвердить |
| `delivery_unavailable` | 400 | способ недоступен для товара |
| `address_required` | 400 | нужен адрес |
| `slot_required` / `slot_unavailable` / `slot_not_supported` | 400 | выбрать время заново |
| `insufficient_funds` | 400 | не хватает денег на остаток — выбрать «при получении» |
| `duplicate_product` / `duplicate_slot` | 400 | ошибка в запросе |

## Кошелёк

Кошелёк — у покупателя: баланс и бонусы. Выручка магазина в кошельки не попадает (приём денег будет на стороне платёжки).

| Часть | Поле | |
|---|---|---|
| Доступно для вывода | `available` | реальные деньги: тратятся и выводятся. В минус — только ручной корректировкой в админке |
| Бонусы | `bonus` | только на покупки, до `BONUS_MAX_SHARE` (50%) суммы покупки |
| Для покупок | `spendable` | не хранится: `available` (без минуса) + `bonus` |

`/me/balance/` → `{"balance": "1500.50", "available": "1500.50", "bonus": "200.00", "spendable": "1700.50"}`
(`balance` = `available`, оставлено для совместимости).

Каждое событие — операция (`WalletOperation`) из проводок по частям кошельков (`WalletTransaction`), всё в одной
транзакции; менять балансы можно только через `wallet.services.post_operation`. Деньги покупки — `apps/orders/payments.py`:

| Событие | Покупатель |
|---|---|
| Оформление, с баланса | `bonus −` (если включил), `available −` остаток |
| Оформление, при получении | `bonus −` (если включил); остаток — наличными при получении |
| Выдача | — |
| Отмена | возврат в те же части |

- Бонусы распределяются по заказам и платной доставке пропорционально суммам (`bonus_amount`) — так при отмене
  известно, сколько бонусов вернуть.
- Кошелёк создаётся вместе с пользователем. Пополнить деньги или начислить бонусы пока можно в админке: правка
  балансов кошелька сохраняется операцией «Корректировка» с проводками на разницу (журнал не редактируется).

## Статусы заказа

Смена статуса — одна форма для всех: `POST .../orders/{id}/status/ {"status": "..."}` → заказ.
Путь зависит от того, кто исполняет доставку (`provider` способа). Правила — `apps/orders/statuses.py` (`TRANSITIONS`).

| Способ | `new` → | `confirmed` → | `ready` → | `completed` |
|---|---|---|---|---|
| Самовывоз (`provider=shop`) | магазин подтверждает | магазин: «Готов к выдаче» | магазин: «Выдан» | |
| Доставка курьером (`provider=market`) | магазин подтверждает | магазин: «Передан курьеру» | курьер: «Доставлен» | |

Отмена (`cancelled`): магазин — из `new`/`confirmed`, для самовывоза и из `ready` («покупатель не пришёл»);
покупатель — только из `new`; курьер — из `ready` для доставки курьером.

- **Кнопки:** в каждом заказе есть `available_statuses: [{"status": "ready", "name": "Готов к выдаче"}]` — куда
  **текущий участник** может перевести заказ. Фронт рисует кнопки по этому списку, правила не дублирует.
- `status_display` зависит от способа: `ready` — «Готов к выдаче» / «Передан курьеру», `completed` — «Выдан» / «Доставлен».
- Недопустимый переход — `400 {"code": "invalid_transition"}`; чужой заказ — `404`.
- **Отмена** возвращает остатки товара и всё, что покупатель заплатил заранее, в те же части баланса (бонусы — в бонусы,
  деньги — в доступные); стоимость доставки — когда отменены все заказы отправки.
  Оплата с баланса и все заказы отменены → `payment_status: refunded`.
- **Выдача** кошельки не меняет. Оплата при получении: когда всё неотменённое выдано → `payment_status: paid`.
- Каждая смена пишется в журнал `OrderStatusChange` (кто, когда, из какого в какой) — видно в админке.
  В админке статус можно поставить любой (кроме выхода из «Выполнен»/«Отменён») — смена идёт через тот же
  `change_status` с возвратами, в журнале участник «Администратор».

| Кто | Эндпоинты |
|---|---|
| Магазин (админка, `is_staff`) | `GET /admin/orders/{id}/`, `POST /admin/orders/{id}/status/` |
| Покупатель | `GET /me/orders/{id}/`, `POST /me/orders/{id}/status/` |
| Курьер (`is_staff`) | `GET /market/orders/` (только доставка службой доставки, `OrderFilter`, `?page=N`; с адресом и магазином), `POST /market/orders/{id}/status/` |

## Ошибки

- Валидация полей — стандарт DRF: `{"field": ["сообщение"], "non_field_errors": [...]}` (400).
- Нарушение бизнес-правила — `{"detail": "Недостаточно товара…", "code": "insufficient_stock"}` (400; `404`, если
  объект не найден; `409`, если данные устарели — `BusinessConflict`). `code` стабилен — по нему фронт может
  ветвиться, `detail` — текст для показа.
  Источник — `BusinessError` из сервисного слоя (`apps/core/exceptions.py`).

## Админка магазина

API для админки магазина (её фронт — бывший кабинет продавца). Все эндпоинты — только для сотрудников (`is_staff`):
без входа и не сотруднику — `403`. Есть ли у пользователя доступ — флаг `is_staff` в `/auth/me/`.

Магазин один, id в адресах не нужен. Через API он не создаётся и не удаляется: на новой установке его заводят в админке
Django (добавить можно, только пока магазина нет); пока не заведён — `404`, код `shop_not_found`. Миграция `shops/0003`
слила существовавшие магазины в магазин с наименьшим id.

| Метод | URL | Описание |
|---|---|---|
| GET    | `/api/v1/admin/shop/` | магазин: публичные поля + служебные |
| PATCH  | `/api/v1/admin/shop/` | `{name?, description?, address?}` |
| GET    | `/api/v1/admin/products/` | товары на продаже (пагинация, фильтры ленты: `q`, `price_min`, ...) |
| POST   | `/api/v1/admin/products/` | `{title, price_usd, delivery_method_ids, quantity?, description?, category_id?, images?, image?, group_id?, characteristic_value_ids?}` — добавить товар |
| GET    | `/api/v1/admin/products/{id}/` | товар |
| PATCH  | `/api/v1/admin/products/{id}/` | `{title?, description?, category_id?, price_usd?, quantity?, images?, image?, delivery_method_ids?, group_id?, characteristic_value_ids?}` — JSON или multipart |
| DELETE | `/api/v1/admin/products/{id}/` | снять с продажи (мягкое удаление) |
| GET    | `/api/v1/admin/products/{id}/images/` | фото товара по порядку `[{id, url}]` |
| POST   | `/api/v1/admin/products/{id}/images/` | multipart `image` — загрузить одно фото в конец → `201 {id, url}` |
| PUT    | `/api/v1/admin/products/{id}/images/order/` | `{"ids": [...]}` — новый порядок всех фото, первое станет обложкой → список фото |
| DELETE | `/api/v1/admin/products/{id}/images/{image_id}/` | удалить фото |
| GET    | `/api/v1/admin/categories/` | дерево категорий (как `/catalog/categories/`) |
| POST   | `/api/v1/admin/categories/` | `{name, parent_id?, slug?, sort_order?}` — новая категория |
| GET    | `/api/v1/admin/categories/{id}/` | категория |
| PATCH  | `/api/v1/admin/categories/{id}/` | `{name?, parent_id?, slug?, sort_order?}` — в том числе перенос |
| DELETE | `/api/v1/admin/categories/{id}/` | удалить пустую категорию |
| GET    | `/api/v1/admin/characteristics/` | характеристики со справочниками значений `[{id, name, category, sort_order, values: [{id, value, sort_order}]}]`; `?category={id}` — доступные товарам категории |
| POST   | `/api/v1/admin/characteristics/` | `{name, category_id?, sort_order?}` — новая характеристика |
| GET    | `/api/v1/admin/characteristics/{id}/` | характеристика |
| PATCH  | `/api/v1/admin/characteristics/{id}/` | `{name?, category_id?, sort_order?}` |
| POST   | `/api/v1/admin/characteristics/{id}/values/` | `{value, sort_order?}` — новое значение в справочник |
| GET    | `/api/v1/admin/product-groups/` | группы вариантов `[{id, name, category, axes: [{id, name}]}]`, `?q=` — поиск по названию, `?category={id}` — подходящие товарам категории |
| POST   | `/api/v1/admin/product-groups/` | `{name, axis_ids, category_id?}` — новая группа |
| GET    | `/api/v1/admin/product-groups/{id}/` | группа; её товары — `/admin/products/?group={id}` |
| PATCH  | `/api/v1/admin/product-groups/{id}/` | `{name?, category_id?, axis_ids?}` |
| GET    | `/api/v1/admin/orders/` | история заказов, новые сверху; фильтры `OrderFilter` (как у покупателя). У заказа — `shipment: {id, delivery_method, slot}` (адрес покупателя — в `/market/orders/`) и `available_statuses` |
| GET    | `/api/v1/admin/orders/{id}/` | заказ |
| POST   | `/api/v1/admin/orders/{id}/status/` | `{"status": "confirmed"}` — сменить статус (см. «Статусы заказа») |
| GET    | `/api/v1/admin/reviews/` | все отзывы (с `author_id`, `author_email`), курсор; фильтры как у отзывов товара + `?product={id}` |
| GET    | `/api/v1/admin/reviews/{id}/` | отзыв |
| DELETE | `/api/v1/admin/reviews/{id}/` | удалить отзыв (модерация; текст чужого отзыва не правится) |

- Списки товаров и заказов пагинированы: `{count, next, previous, results}`, `?page=N`, по 20.
- Денежные поля приходят строками (`"79990.00"`) — без потери точности.
- `address` — где забрать товар при самовывозе (павильон, ряд, место), до 255 символов; пока необязателен,
  но без него нельзя выбрать самовывоз (см. ниже). Стереть адрес, пока у товаров магазина на продаже
  выбран самовывоз, нельзя: `400 {"address": [...]}`, код ошибки `shop_address_in_use`.
- Товар не удаляется физически (на него ссылаются заказы), а получает статус `archived`.
- `shop` и `status` товара через PATCH не меняются; новый товар всегда попадает в магазин.

### Способы доставки товара

- Запись: `delivery_method_ids: [1, 2]` — **обязательно при создании** (минимум один), в PATCH — заменяет набор целиком
  (пустой список нельзя). В multipart — повторяющееся поле `delivery_method_ids`.
- Принимаются только способы из `available_for_shop` (неактивные / несуществующие — 400).
- Самовывоз силами магазина (`kind=pickup`, `provider=shop`) требует адрес магазина: без него
  `400 {"delivery_method_ids": ["Укажите адрес магазина, чтобы выбрать: ..."]}`, код `shop_address_required`.
  Проверяется, когда передан `delivery_method_ids`; PATCH других полей набор способов не перепроверяет.
- Чтение: `delivery_methods` — полные объекты как в `/delivery/methods/` (в админке и на странице товара).
- Лента фильтруется по способу: `?delivery_method={id}`.

### Фото товара

У товара до `PRODUCT_IMAGES_MAX` (10) фото. Первое по порядку — **обложка**.

- `image` — обложка: строка-URL (`/media/products/<uuid>.png`) или `null`. Есть в ленте, корзине,
  заказах, админке и на странице товара. **Фронт должен показывать заглушку при `null`.**
- `images` — все фото по порядку `[{id, url}]`, `images[0].url == image`. Есть в админке и на
  странице товара (в карточках ленты нет).
- Загрузка по одному — `POST .../products/{id}/images/` (multipart, поле `image`): фото встаёт в конец,
  у первого загруженного оно же становится обложкой. Так фронт может показать прогресс каждого файла,
  а одно битое фото не отменяет остальные.
- При создании товара (и в `PATCH`) можно сразу передать `images` повторяющимся полем multipart —
  файлы добавятся в конец.
- Порядок — `PUT .../images/order/ {"ids": [...]}`: нужно передать все фото товара, каждое один раз,
  иначе `400`, код `image_order_mismatch` (список устарел — перечитайте `GET .../images/`).
- Удаление — `DELETE .../images/{image_id}/`. Если удалили обложку, ей становится следующее фото.
- Больше лимита — `400`, код `too_many_images` (в форме товара — ошибка поля `images`).
- **Устарело, но работает:** запись `image` в `POST`/`PATCH` товара. Файл заменяет обложку
  (или добавляет первое фото), `null` / пустое `image=` в multipart удаляет обложку.
- Проверки: файл должен быть картинкой (Pillow), размер — до `PRODUCT_IMAGE_MAX_MB` (5 МБ).
  Имя файла заменяется на случайное. Файлы удаляются с диска после успешного сохранения.
- Если файл пропал из хранилища — API не падает. В dev Vite проксирует `/media` на Django;
  в prod `/media/` раздаёт nginx (или подключается S3-хранилище — URL станут абсолютными).
- Позиции заказа хранят снимок названия и цены на момент покупки.

## Категории

Дерево любой глубины. Товар можно положить в любую категорию, в том числе в раздел с подкатегориями;
раздел показывает свои товары вместе с подкатегориями. Обход дерева — `catalog/categories.py`.

- Список (`/catalog/categories/`, `/admin/categories/`) — плоский, в порядке дерева: родитель, затем его подкатегории
  по `sort_order` и названию. `[{id, name, slug, parent_id, sort_order, depth, products_count}]`: `depth` — уровень
  (верхний — 0), `products_count` — товары на продаже вместе с подкатегориями. Вложенное меню фронт собирает по `parent_id`.
- Товары раздела — лента `?category={id}` (с подкатегориями; та же фильтрация в `/admin/products/`).
- Товар: в админке `category: {id, name, slug} | null`, запись — `category_id` (`null` — убрать из категории);
  на странице товара — `category_path` от верхнего уровня до категории товара («хлебные крошки»), без категории — `[]`.
  Категория пока необязательна: товар без неё есть в общей ленте, но ни в одном разделе.
- `slug` — часть адреса страницы раздела (`smartfony`). Не передан — генерируется транслитом из названия (при совпадении —
  `smartfony-2`); при переименовании не меняется, чтобы не ломать ссылки.
- Названия у соседних категорий не повторяются (без учёта регистра и ё/е) — `400 {"name": [...]}`.
- Перенос (`parent_id`) разрешён куда угодно, кроме самой категории и её подкатегорий — `400`, код `category_cycle`.
- Удалить можно только категорию без подкатегорий, привязанных характеристик и групп и товаров на продаже — иначе `400`,
  код `category_not_empty`. Снятые с продажи товары остаются без категории.

### Характеристики категорий

У характеристики есть `category` — где она доступна: в этой категории и всех её подкатегориях. `null` — во всех
категориях. Привязывают туда, где характеристика общая для всей ветки: «Цвет» — общий, «Встроенная память» —
к «Смартфонам», «Размер корпуса» — к «Смарт-часам». Значения у характеристики одни на все категории.

- Форма товара берёт `GET /admin/characteristics/?category={id}` — общие характеристики, привязанные к категории и к
  категориям выше.
- Название уникально в ветке (без учёта регистра и ё/е): среди общих, категорий выше, самой категории и её подкатегорий —
  иначе `400 {"name": [...]}`. «Тип» у наушников и «Тип» у телевизоров — можно.
- **Строго при сохранении товара:** все его характеристики доступны в его категории (товару без категории — только общие),
  иначе `400`, код `characteristic_not_in_category`. Проверяется и при смене категории товара: перенося товар, передайте
  подходящие `characteristic_value_ids`.
- **Группа вариантов** тоже привязана к категории (`category`): её товары лежат в этой категории и подкатегориях,
  оси — из характеристик, доступных в ней. Группа без категории — товары где угодно, оси только общие. Строго при
  записи: ось не из категории группы — `400`, код `variant_axis_not_in_category`; товар вне категории группы (при
  сохранении товара или смене категории группы) — `400`, код `variant_product_outside_category`. Поле «Группа» в форме
  товара — `GET /admin/product-groups/?category={id}`: группы без категории, этой категории и категорий выше.
- **Мягко при перестройке:** перенос категории (`parent_id`) и характеристики (`category_id`) ничего не проверяет.
  Что после этого стало недоступно в категории товара — на витрине скрыто, в админке у характеристики товара
  `in_category: false` (поправьте товар). Если товар оказался вне категории своей группы или недоступна ось
  группы — у товара не показываются варианты, а сам он не попадает в кнопки других товаров группы.

## Варианты товара

Варианты — товары одной модели, которые различаются цветом, памятью и т.п. (как в DNS). Каждый вариант — отдельный
товар со своей страницей, ценой, остатком и фото; в корзину и заказы кладётся он сам. Логика — `catalog/variants.py`.

- **Характеристика** («Цвет», «Встроенная память») и её **справочник значений** («Чёрный», «256 ГБ»). Значения
  только выбираются из справочника, поэтому «Чёрный» и «черный» не станут разными кнопками; повтор значения
  в другом написании (регистр, ё/е) при создании — `400`. `sort_order` задаёт порядок строк и кнопок
  («512 ГБ» перед «1 ТБ»). Переименование и удаление — в админке Django; значение, которое стоит у товаров, удалить нельзя.
- **Характеристики товара** — по одному значению на характеристику. Запись — `characteristic_value_ids: [11, 21]`
  (id значений; характеристика берётся из значения), в PATCH заменяет набор целиком. Два значения одной
  характеристики — `400`, код `characteristic_repeated`. Чтение — `characteristics: [{characteristic_id, name, value_id, value, in_category}]`
  в админке и на странице товара (на витрине — только `in_category: true`, см. «Характеристики категорий»).
- **Группа вариантов** («iPhone 13») — своей страницы нет, только связывает товары. `axes` — характеристики, по которым
  различаются её товары, `category` — где лежат её товары (см. «Характеристики категорий»). Товар в группу — `group_id`
  (`null` — убрать из группы), чтение — `group: {id, name} | null`.
- Правила для товаров группы на продаже (снятые с продажи не участвуют):
  - у товара заполнены все оси группы — иначе `400`, код `variant_axis_missing`;
  - двух товаров с одинаковыми значениями осей нет — иначе `400`, код `variant_duplicate`.
  Проверяются при записи `group_id` / `characteristic_value_ids` и при смене осей группы (`axis_ids`): новую ось сначала
  заполняют у товаров группы, потом добавляют в группу.
- **Кнопки вариантов** на странице товара — поле `variants`, строится по товарам группы при каждом запросе:

```json
"variants": [
  {"characteristic_id": 1, "name": "Цвет", "options": [
    {"value_id": 10, "value": "Чёрный", "product_id": 2, "selected": true,  "exact": true,  "in_stock": true},
    {"value_id": 11, "value": "Синий",  "product_id": 6, "selected": false, "exact": false, "in_stock": true}
  ]}
]
```

  Строка — ось группы, кнопки — значения, которые есть у товаров группы на продаже. Кнопка ведёт на товар с этим
  значением и остальными осями как у текущего; если такого нет — на ближайший (больше совпадающих осей, при равенстве —
  совпадают более ранние оси), тогда `exact: false` (фронт может подписать, что сменятся другие параметры).
  `selected` — значение текущего товара, `in_stock` — есть ли товар, на который ведёт кнопка. У товара без группы — `[]`.

## Отзывы

Отзыв — о конкретном товаре (варианте): оценка `rating` от 1 до 5 и текст из трёх полей — `pros` (достоинства),
`cons` (недостатки), `comment` (комментарий), каждое до 2000 символов. Нужно хотя бы одно из трёх — иначе
`400 {"non_field_errors": [...]}`. Логика — `apps/reviews`.

- Оставить отзыв может любой вошедший пользователь, один на товар: второй — `400`, код `review_exists` (свой отзыв
  меняют через PATCH). Товар — только на продаже; у готового отзыва товар не меняется.
- Свой отзыв на товар — `GET /me/reviews/?product={id}`: пустой `results` — отзыва ещё нет.
- Сотрудник может удалить любой отзыв (`/admin/reviews/`, админка Django).
- Оценка товара — кеш `rating` и `reviews_count` у товара, пересчитывается при каждом изменении отзывов.

```json
{"id": 3, "product_id": 7, "product_title": "iPhone 15", "author_name": "Анна", "rating": 4,
 "pros": "Экран", "cons": "Батарея", "comment": "", "created_at": "...", "updated_at": "..."}
```

`author_name` — имя автора, без имени — «Покупатель»; email на витрине не показывается.

Параметры списков отзывов (`ReviewFilter` — один для витрины, «моих отзывов» и админки):

| Параметр | Пример | |
|---|---|---|
| `rating` | `5`, можно несколько: `?rating=5&rating=4` | оценка |
| `sort` | `new` (по умолчанию), `rating_desc`, `rating_asc` | |
| `page_size`, `cursor` | | как в ленте товаров |

## С этим товаром часто покупают

`GET /api/v1/catalog/products/{id}/bought-together/` — до 5 карточек товаров (как в ленте), которые чаще всего
покупали вместе с этим, сначала самые частые. Пустой список — данных пока нет; снятый с продажи товар — `404`.

- «Вместе» — в одной покупке (всё, что оформлено одной кнопкой), даже если она разделилась на заказы по способам
  доставки. Отменённые заказы не считаются. Порядок — по числу совместных покупок, при равенстве выше тот, с кем
  покупали позже. Товары не на продаже не показываются.
- Считается по моделям: товар группы вариантов — это вся группа. У всех вариантов группы топ общий (и у ещё не
  купленных), другие варианты самого товара в него не попадают. Группа другого товара занимает одно место: покупка
  с двумя цветами геймпада считается один раз, показывается вариант, который чаще покупали вместе (на продаже,
  по возможности в наличии).
- Хранится только топ — 5 строк на товар (`recommendations.BoughtTogether`), страница читает его по индексу.
  Пересчёт товара читает только покупки с этим товаром, а не все заказы.
- Когда пересчитывать — переменная `BOUGHT_TOGETHER_ON_PURCHASE`:
  - `True` (по умолчанию) — сразу после каждой покупки, только её товары (после коммита: ошибка пересчёта покупку
    не откатит, а попадёт в лог);
  - `False` — только по расписанию: cron раз в сутки на `python manage.py refresh_bought_together` (пересчитывает
    все товары). Команду можно запускать и при `True` — например, чтобы учесть отменённые заказы: отмена топ сразу
    не меняет.

## Цены и курс доллара

Цена товара хранится в долларах (`Product.price_usd`), а покупатель видит и платит рубли: `price` в карточке,
корзине, оформлении и заказе = `price_usd` × курс, округлённое до `PRICE_RUB_STEP` (по умолчанию до рубля).
Админка магазина задаёт `price_usd` и получает обе цены. В позицию заказа пишется рублёвая цена на момент
оформления — потом курс на заказ не влияет. Фильтр `price_min`/`price_max` — в рублях, ровно по показанной цене.

`GET /api/v1/currency/usd/` — текущий курс: `{"rate": "82.8879", "date": "2026-10-21"}` (`date: null` — курс
задан настройкой). Нет ни одного курса — `503`, `code: rate_unavailable`.

- Курс — официальный курс ЦБ на сегодня (`https://www.cbr.ru/scripts/XML_daily.asp`, бесплатно, без ключа).
  Его запрашивают при первом обращении и держат в кеше до полуночи по Москве, cron не нужен. Каждый полученный
  курс сохраняется в `currency.ExchangeRate` (Django admin → «Курсы валют»).
- ЦБ недоступен — берётся последний сохранённый курс, ЦБ спрашивается снова через 5 минут. Миграция засеяла
  курс на 21.10.2026 — по нему же переведены в доллары прежние рублёвые цены (`catalog/0011`).
- `USD_RUB_RATE` — свой постоянный курс вместо ЦБ. В тестах курс 1 и шаг 0.01: цена в рублях равна цене
  в долларах; пересчёт по настоящему курсу проверяют тесты `apps/currency`.

## Соглашения

- **Одна логика на сущность — для всех сторон.** Один `FilterSet` на сущность (`ProductFilter`, `OrderFilter`),
  одна пагинация на тип списка (наследники `core.pagination.KeysetPagination`), один базовый сериализатор,
  от которого наследуются варианты для админки/покупателя/публики (`OrderSerializer` → `OrderAdminSerializer`,
  `BuyerOrderSerializer`; `ShopPublicSerializer` → `ShopAdminSerializer`). Кто что видит — задаёт queryset view,
  а не отдельный фильтр. Никаких `UserGoodsFilter`/`SellerProductFilter`.
- **Маршруты по аудиториям** собираются в `config/api_v1.py` из доменных приложений: `admin_urls.py` → `/admin/`,
  `me_urls.py` → `/me/`, `urls.py` → публичные.
- **Новое доменное приложение** — `backend/apps/<name>/`, регистрируется в `LOCAL_APPS` и подключается в `config/api_v1.py`.
- **Бизнес-логика — в сервисном слое** (`apps/<name>/services.py`), а не во view/serializer.
  Там же задаются границы транзакций (`transaction.atomic`, `select_for_update`) —
  это позволит делать атомарные операции (заказы, остатки, платежи) без переписывания view.
- **БД** задаётся через `DATABASE_URL` — переход с SQLite на PostgreSQL без изменений кода.
- **API версионируется** префиксом `/api/v1/`.
